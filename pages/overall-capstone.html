Personal Reflection

Discovering Design Patterns

Before the development of my capstone, I did not know much about software design patterns, nor did I understand their value. During the development of my capstone, I quickly ran into problems with code complexity. It became difficult to implement new features, because my code had no structure and was tightly coupled. After realizing that development would be impossible with an unorganized code style, I turned to design patterns to help develop sustainable and clean code.

The transition to implementing design patterns was not easy, because I initially did not like using a predefined solution. When working on a project, I like creating everything from scratch. Using other people’s solutions feels like cheating to me, because they work well, and I did not come up with them. Since I viewed using design patterns the same as using predefined solutions to software development problems that I did not create myself, I felt like I was going against my consciousness.

To solve this dissonance, I came to terms with using design patterns instead of brute forcing my own solutions. Everything in this world is based on and informed by previous iterations of themselves. Picasso did not create his artwork in a void, and Galileo did not prove the heliocentric model without the theories of Copernicus, so it is not a problem if I develop an efficient solution based on the efforts of those before me. I am not stealing work by using design patterns, nor am I cutting effort. It is the natural progression of human advancement. I did not change my view regarding design patterns, I accepted it.

Balancing Design Patterns and Personal Judgement

During my implementation of design patterns into the diagram editor website, I encountered scenarios where certain aspects of a pattern did not fit the problem. For example, I have hit detection logic contained in each shape’s class, which is only supposed to contain data logic under the model-view-controller pattern. My two choices were to ignore the pattern and implement the solution I thought made sense, or strictly follow the pattern even if the solution seemed convoluted to me.

This was a difficult choice for me because I like making choices backed by proven reason and theory. Going against the pattern would feel like going against logic. However, certain implementations of patterns in my project were not justifiable. I had to take the risk of adjusting the patterns to fit my problems, even if it meant feeling like I was making my code improper.

After implementing my own versions of design patterns, I noticed that my code was cleaner than before. My adjustments resulted in significantly less coupling, fewer lines of code, and more readable code. I made the mistake of putting design patterns on a pedestal and viewing them as absolute solutions, when their true purpose was to be guides. I lacked confidence in my development and problem-solving skills, so I was uncomfortable assuming the role of architect. However, my judgement as a developer is what makes my work unique and worthwhile. If I forsook my authority to a third party, then I would be no more than a static conduit.

Adjusting to Development Demands

Midway through development of the diagram editor website, I realized that my work was not what I expected it to be. My expectations for web development were work involving HTML structure, managing numerous event listeners, user interface design, and more. However, the work around the diagram editor did not have anything to do with those topics. The diagram editor involved work regarding class design and relationships, visual rendering, and user input handling.

The misalignment in expectations and reality discouraged me. I wanted to quit development on the diagram editor and move onto something else, but that was not an option. At that point, the capstone project was halfway through. The choice was made for me. I would have to grind through and complete the diagram editor.

To cope with my discouragement, I aimed to shift my mindset. Industry-grade projects do not often have the luxury of stopping whenever the employees feel like it. This capstone project is no different. At every given moment, I carry the weight of responsibility and my future. It is a challenge. It is not necessary for me to be enthusiastic about this challenge, I just have to be enthusiastic about facing the challenge.

Scrapping Features

At the start of this project, I envisioned a diagram editor with rich functionality. I planned to have a diagram editor workspace with a functionality matching LucidChart, collaboration capability, and an accessible and aesthetic user interface that would span a home page and the diagram editor workspace. With minimal research and planning, I thought these goals to be realistic and achievable.

Throughout the duration of the project, I faced many unexpected complications that delayed the implementation of features. Since I had limited time to work on the project, these delays meant certain features had to get scrapped. Ultimately, I only had a diagram editor workspace with essential functionality, which included adding, modifying, and deleting shapes.

The lack of features in my final product compared to my envisioned product was heavily discouraging. I associated the level of implementation with my level of competence. I had to step back to see that, despite the lack of implementation, I still put in effort throughout the project. Competence is not measured solely in raw output. I failed to meet my expectations, but I tried, and I learned.

Conclusion

This capstone project was my first experience working on a large project that spans multiple months. Choosing a project topic that I lacked experience in challenged me greatly, but it taught me many things that I would never have learned in any university class.
